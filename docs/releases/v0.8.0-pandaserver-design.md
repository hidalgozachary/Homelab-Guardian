# Homelab Guardian v0.8.0 — PandaServer Integration Design

## Status

Proposed

## Purpose

Version 0.8.0 makes PandaServer, running Unraid, the first production host monitored by Homelab Guardian.

This release establishes the operational report contract that collectors, scoring, renderers, and notifications will use.

The application must provide a clear answer to this question:

> Is PandaServer operating normally, and is any action required?

---

# Design Goals

Version 0.8.0 must:

- Collect live operational information from PandaServer
- Detect Unraid and Docker conditions accurately
- Report unavailable integrations honestly
- Continue running when an optional collector fails
- Produce one standardized operational report
- Use the same health data for Terminal, JSON, Discord, and Gmail
- Remain entirely read-only
- Avoid restarting, stopping, deleting, or modifying infrastructure
- Preserve Unraid native alerts as an independent safety layer

---

# Non-Goals

Version 0.8.0 will not:

- Restart unhealthy containers automatically
- Delete Docker images
- Perform Docker updates
- Start parity checks
- Run extended SMART tests
- Modify array assignments
- Repair filesystems
- Restore backups
- Expose PandaServer publicly
- Replace Unraid native notifications
- Replace Uptime Kuma

Automatic remediation will be considered in a later release and must remain disabled by default.

# Collector Ownership

Each collector owns a clearly defined domain.

## Host Collector

File:

```text
collectors/host.py
```

Responsibilities:

- Hostname
- Operating system
- Platform
- Kernel
- Architecture
- CPU model
- CPU utilization
- Memory utilization
- Uptime
- Boot time
- Load average
- CPU temperature when supported

The Host Collector must remain usable on non-Unraid systems.

---

## Unraid Collector

File:

```text
collectors/unraid.py
```

Responsibilities:

- Detect Unraid
- Unraid version
- Array state
- Assigned-device count
- Problem-device count
- Missing-device count
- Parity validity
- Last parity-check details
- Unraid-specific configuration state

The Unraid Collector must return `UNAVAILABLE` on non-Unraid systems.

---

## Storage Collector

File:

```text
collectors/storage.py
```

Responsibilities:

- Array capacity
- Array utilization
- Cache capacity
- Cache utilization
- Filesystem types
- Individual disk inventory
- Disk temperatures
- SMART overall status
- Device roles
- Device names
- Device models

It must not start SMART tests during normal report execution.

---

## Docker Collector

File:

```text
collectors/docker.py
```

Responsibilities:

- Docker service state
- Running containers
- Stopped containers
- Unhealthy containers
- Container names
- Health-check results
- Restart counts
- Optional container uptime

It must not restart, stop, remove, or update containers.

---

## Network Collector

File:

```text
collectors/network.py
```

Responsibilities:

- Internet reachability
- HTTP response time
- DNS resolution
- Local address information where appropriate

Existing network checks will remain supported.

---

## Services Collector

File:

```text
collectors/services.py
```

Responsibilities:

- Expected-service inventory
- Installed or not installed
- Running or stopped
- Healthy or unhealthy
- Pi-hole operational status
- Uptime Kuma operational status
- Tailscale connection status
- Future services such as Immich and Jellyfin

The distinction between these states is important:

```text
NOT INSTALLED
NOT CONFIGURED
STOPPED
UNHEALTHY
HEALTHY
UNAVAILABLE
```

A service that is not installed must not lower the health score unless it is configured as required.

---

## Backup Collector

File:

```text
collectors/backups.py
```

Responsibilities planned for v0.9.0:

- Appdata backup status
- Flash backup status
- Last successful backup
- Backup age
- Retention status
- Verification status

For v0.8.0, it may return:

```text
NOT IMPLEMENTED
```

This should not lower the health score.

---

# Collector Result Contract

Every collector returns a standardized result.

```json
{
  "name": "unraid",
  "status": "COLLECTED",
  "available": true,
  "data": {},
  "error": null
}
```

Valid collector statuses:

```text
COLLECTED
UNAVAILABLE
FAILED
NOT_IMPLEMENTED
```

Definitions:

- `COLLECTED`: The collector completed successfully.
- `UNAVAILABLE`: The platform or integration does not exist on this host.
- `FAILED`: The collector was expected to run but encountered an error.
- `NOT_IMPLEMENTED`: The collector is intentionally reserved for a future release.

A failed optional collector must not crash the application.

The complete JSON report should evolve toward this structure:

```json
{

    "report_id": "unique-id",
    "generated_at": "2026-08-05T17:00:00-04:00",
    "guardian_version": "0.8.0",
    "host": "PandaServer"
  },
  "health": {
    "status": "HEALTHY",
    "score": 100,
    "issues": [],
    "issue_summary": "No monitored issues detected."
  },
  "host": {},
  "unraid": {},
  "storage": {},
  "docker": {},
  "network": {},
  "services": {},
  "backups": {},
  "collectors": {}

```

The schema will be introduced incrementally. Existing report keys must remain supported until a deliberate migration is completed.

# Health Status

Supported operational statuses:

```text
HEALTHY
WARNING
CRITICAL
UNKNOWN
```

## Healthy

Conditions are operating within expected parameters.

## Warning

A condition requires attention but does not indicate immediate loss of service or protection.

Examples:

- Storage usage above warning threshold
- One configured container stopped
- Elevated disk temperature
- Backup becoming stale
- Optional collector failure

## Critical

A condition represents immediate operational risk.

Examples:

- Array not started
- Missing or disabled assigned disk
- Parity invalid
- SMART failure
- Docker unavailable when required services depend on it
- Required service unavailable
- Cache or array critically full

## Unknown

The system cannot determine operational health reliably.

This may occur when several required collectors fail simultaneously.

---

# Health Score Philosophy

The health score provides an at-a-glance summary but does not replace detailed status information.

Suggested weighting:

| Domain | Maximum Points |
|---|---:|
| Host | 10 |
| Array and parity | 25 |
| Storage and disks | 20 |
| Docker | 15 |
| Network and DNS | 10 |
| Required services | 10 |
| Backups | 10 |
| Total | 100 |

During v0.8.0, backup points may remain neutral until backup collection is implemented.

Critical conditions may override the numeric score and force `CRITICAL`.

---

# Required and Optional Services

Services must be configurable.

Example:

```json
{
  "services": {
    "required": [
      "pihole",
      "uptime-kuma"
    ],
    "optional": [
      "dozzle",
      "immich",
      "jellyfin",
      "audiobookshelf",
      "grafana",
      "prometheus",
      "loki",
      "nextcloud"
    ]
  }
}
```

Rules:

- A required service that is stopped or unhealthy affects health.
- An optional service that is not installed does not affect health.
- A configured optional service that becomes unhealthy may generate a warning.
- Future services can be added without changing the report architecture.

---

# Renderer Behavior

## Terminal

Should display the complete operational report in readable text.

## JSON

Should contain all collected data, including verbose details that may not appear in notifications.

## Discord

Should use:

- Green embed for `HEALTHY`
- Yellow embed for `WARNING`
- Red embed for `CRITICAL`
- Gray embed for `UNKNOWN`
- Emojis
- Concise but complete operational summary
- Direct Homelab Guardian webhook

## Gmail

Should use the same section order and wording as Discord.

HTML formatting may be used, but the data must remain consistent with Discord and JSON.

---

# Native Unraid Notifications

Homelab Guardian complements rather than replaces Unraid notifications.

Unraid remains responsible for immediate native alerts such as:

- SMART warnings
- Disk errors
- Array stopped events
- Parity events
- Temperature alerts
- System notifications

Homelab Guardian provides:

- Consolidated operational summaries
- Cross-domain health scoring
- Service awareness
- Historical intelligence
- Backup verification
- Future automation

# v0.8.0 Implementation Order

The release will be built in this order:

1. Collector framework
2. Unraid platform collector
3. Host collector
4. Storage collector
5. Docker collector
6. Services collector
7. Tailscale status
8. Health-scoring integration
9. Operational report v2
10. Discord and Gmail alignment
11. PandaServer deployment
12. Production validation
13. Documentation and release notes

---

# Validation Requirements

Before v0.8.0 is complete:

- All automated tests must pass
- CI must pass
- Collectors must run safely on macOS
- Collectors must run successfully on PandaServer
- Report values must be compared with the Unraid GUI
- Array state must be accurate
- False empty-slot disk warnings must not return
- Docker counts must match Unraid
- Discord output must render correctly
- No secrets may appear in logs or reports
- No collector may modify infrastructure

---

# Rollback

PandaServer integration must be deployable separately from the stable branch.

Rollback should require only:

- Disabling the scheduled Homelab Guardian launcher
- Restoring the prior application version
- Retaining Unraid native monitoring and the existing User Script report

No data migration should be required for v0.8.0.
